# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This repository hosts a Japanese-language graduate-level textbook on **investment science** (Markowitz portfolio theory through continuous-time optimization). It is *content*, not a software product — the "code" here is a custom Markdown → LaTeX pipeline plus matplotlib figure generators that compile the book to PDF.

## Versioning convention

Each major revision lives in its own top-level directory `vN/` (currently `v1/`, `v2/`). When the user asks for a new version, **copy the latest version directory** (`cp -r v2 v3`) and edit there — do not mutate older versions in place. The README inside each `vN/` describes that version's distinguishing focus (v1: text-only; v2: figures added).

## Build pipeline

The pipeline is intentionally minimal and self-contained — there is no pandoc, no Makefile, no CI. Every version directory ships with its own `build.py` and (from v2 onward) `figures/gen_figures.py`.

**Standard build (run inside a `vN/` directory):**

```bash
# regenerate figures if any .py under figures/ changed
../.venv/bin/python figures/gen_figures.py

# Markdown → LaTeX
python3 build.py

# LaTeX → PDF (run twice so TOC resolves)
lualatex -interaction=nonstopmode book.tex
lualatex -interaction=nonstopmode book.tex

# clean up aux files
rm -f book.aux book.log book.out book.toc
```

**Why `lualatex` and not `xelatex` or `pdflatex`:** the book mixes Japanese with heavy math. `build.py` loads `luatexja-preset` for Japanese typesetting, which requires lualatex specifically. pandoc is intentionally not used — the project ships its own tiny Markdown parser tuned to the constructs the book actually uses.

**Python environment:** a single `.venv/` at the repo root is shared across all versions (matplotlib + numpy + scipy installed via `python3 -m venv .venv && .venv/bin/pip install matplotlib numpy scipy`). Use `../.venv/bin/python` from inside any `vN/figures/` directory.

## How the Markdown → LaTeX converter works (`build.py`)

`build.py` is **not** a general Markdown processor. It only handles the subset of Markdown the chapters actually use, and silently drops anything else. Key behaviors:

- **File order is the chapter order.** The `CHAPTERS` list at the top of `build.py` controls inclusion and order. `README.md` is intentionally excluded.
- **Top-level `#` in each chapter file becomes `\chapter{}`.** `##` → `\section`, `###` → `\subsection`. Avoid using `#` mid-file.
- **Math is protected before LaTeX-escaping.** `$...$` and `$$...$$` regions are stashed as placeholders, escaping is applied to the surrounding text, then math is restored. If you find math being corrupted, check `protect_math` / `restore_math` in `build.py`.
- **Inter-chapter navigation links** (`[← 第N章](...)` / `[次章 → ...]` style) are stripped — they only make sense in the HTML/GitHub view, not in the PDF.
- **Images** are `![caption](figures/foo.png)` on a line by itself; these become `\begin{figure}[H]...\end{figure}` blocks. The `[H]` placement requires the `float` package (already in the preamble).

When you add a new Markdown construct (e.g., footnotes, code blocks with syntax highlighting), you must extend the parser — it will not "just work."

## How `gen_figures.py` works (v2+)

All figures are generated by a single script with a function per figure. Two macOS-specific details that matter:

- **Japanese fonts:** the script registers `/System/Library/Fonts/ヒラギノ角ゴシック W4.ttc` via `font_manager.fontManager.addfont` and sets it as the default `font.family`. Without this, every Japanese character in a figure renders as a tofu box. On non-Mac systems substitute another CJK font path here.
- **matplotlib mathtext is not full LaTeX.** It rejects `\le`, `\iff`, and many other common macros — use `\leq`, `\Leftrightarrow`, etc. When a figure fails with `Unknown symbol: \xxx`, the fix is almost always to swap the mathtext command, not to escape the backslash.

To add a new figure: define `fig_xxx()` in `gen_figures.py`, call it from `main()`, then reference the resulting PNG from the relevant chapter with `![caption](figures/xxx.png)`. The build pipeline does not auto-detect new figures from disk.

## Codex との協働プロトコル

### 役割分担

| 役割 | 担当 |
| --- | --- |
| Claude (PI/supervisor) | 統合・方向判断・出力評価・narrative 作成 |
| codex exec (大学院生/postdoc) | 実際の手を動かす作業（code・文献調査・データ取得・解析） |

### CLI の使い方

codex は `/opt/homebrew/bin/codex` にある。非対話的に呼び出す：

```sh
codex exec -m gpt-5.5 -c model_reasoning_effort=high "{prompt}"
```

モデルは **gpt-5.5**、reasoning effort は **high** を既定とする。

**重要**: prompt は heredoc (`<<EOF ... EOF`, `<<'EOF' ... EOF`) で渡さないこと。 必ず `codex exec "..."` の引数として一つの文字列で渡す。複数行が必要なら `\n` を埋め込むか、改行を含むダブルクォート文字列にする（bash はそのまま受け取る）。heredoc 経由だと codex CLI が prompt を取り違える事例があるため。

例：

```sh
codex exec "Read notebooks/2026_04_29-msa_consensus_depmap/src/eval_b2_auroc.py and summarize the scoring pipeline in 5 bullet points"
```

### いつ codex exec に委譲するか

- 境界が明確な subtask（スクリプト作成、関数リファクタ、ノートブック要約）
- セカンドオピニオン・クロスチェック
- 並列化できる断片（会話の全 context が不要なもの）
- 仮説の iterative critical review（多ラウンドパターン、特にユーザーが明示的に invoke したとき）

### "codex と / に / で" トリガー

ユーザーが codex に言及したら 1 回で終わらず **3–5 ラウンド**の議論を行う：

- Round 1: framing — 既知/未知の整理
- Round 2: Round 1 の最も有益な branch を深掘り
- Round 3: critical assessment / counterargument / verification
- Round 4–5: synthesis、weakest-link 特定、actionable verdict

各ラウンド間で codex の回答をチャットで要約し、ギャップを突くか弱い主張を challenge する follow-up prompt を作る。

### Practical tips

- File paths・expected output・prior findings を prompt に明記する（codex は fresh session で起動）
- `--skip-git-repo-check` を使用する
- PMIDs / DOIs / accessions を cite-back させて verify する
- Codex sandbox は read-only がデフォルト → ファイル書き込みは PI 側（Claude）で実行
- 必ず critical review を行う（codex は citation を hallucinate したり、データの特殊事情を見落とすことがある）

## Things to leave alone

- `v1/` is a frozen baseline. Do not edit it when asked to improve "the book" — work in the latest `vN/` (or create the next one).
- The `book.tex` and `book.pdf` files inside each version are build artifacts. Edit the Markdown sources, not the generated `.tex`.
- The chapter list in `build.py` (`CHAPTERS = [...]`) is the source of truth for ordering; do not rely on filesystem sort order.
